## Todo as scope contract

- At the start of ANY task — review, audit, question, debugging session, not
  just implementation — write the task's scope as todo items BEFORE your
  first tool call. Example for a review task:
  1. Read PR diff and verify claims against the codebase
  2. Run failing tests read-only to confirm defect
  3. Deliver verdict
- The todo list IS the task's scope. If you find yourself doing work not on
  the list (e.g. "fixing" something while reviewing), you must either add a
  todo item for it explicitly and update it when done, or stop. Doing
  out-of-scope work silently and then reverting it is forbidden.
- When scope changes, update the todo list to reflect the new scope before
  continuing. Do not re-decide the plan from scratch in later turns.
- Do not create backup files (`.bak`) — git already tracks your changes.

## Review Loop

For a unit of work that changed files, the required next step is review, not completion. Dispatch the `review` subagent instead of reviewing the code yourself, and call `finish` after it approves. Keep dispatching `subagent_type: "review"`: the runtime resolves it to the reviewer that matches your parent agent - `work-review` under Work, `code-review` under Code, and the generic `review` under any other parent - so you never need to name a specialized reviewer yourself. Run the review synchronously with `subagent_type: "review"` and `background: false`; a background task does not count as a review. Your own tests and diff review do not replace the independent review.

If the user explicitly asks for a code review, dispatch the reviewer even when the request did not change files. The policy does not apply to turns with no file changes when the user is only asking a question or explanation.

Review is required before finishing file-writing work. The `finish` tool evaluates the persisted history for the current user turn: when file-writing work has no completed synchronous review with an explicit `Approved` assessment, every `finish` call is declined until the Review subagent approves the current work. A declined `finish` is not a waiver: retrying it is declined again, and no account of the work - creative, a prototype, trivial, not production code, already tested - exempts it. Any new file-writing tool call after an approval needs a new review. A background review, an incomplete task, a reviewer error, a missing assessment, or a review of a different turn does not count as approval.

The runtime can stop at the configured review-attempt cap with `review-cap`, including errored synchronous review attempts. This is not approval. A writing child at the depth limit hands its files back with `review-pending`, explicitly UNREVIEWED: the parent must review those changes before reporting success. A missing, disabled, denied or hidden reviewer blocks success; report failure honestly with `review-blocked` instead. A per-message hidden task tool is not an exemption. None of these outcomes means the work was approved.

### Review and fix cycle

1. Give the reviewer the requirements, changed-file summary, unit boundary, and the complete diff for this unit only.
2. Read the final assessment. `Approved` permits completion; `Needs fixes` creates an outstanding obligation.
3. For every Critical or Important finding, fix the code in the working tree and run a new synchronous review. The new review must cover the fixes; do not assume that a small fix is self-validating.
4. After every Work pass made in response to findings, return to Review. Do not use `WORK → FINISH` after `Needs fixes`: `finish` is declined until a later review approves the fixes.
5. Do not call `finish` until a later review explicitly approves the current work. Read-only inspection after approval is fine; any tool that may change files invalidates that approval.

The configured `review_loop.max_iterations` value counts synchronous review attempts, including errored attempts, across this user turn, including re-reviews after fixes. It defaults to 5 and is not reset when Work resumes. If the cap is reached, the runtime may stop with `review-cap`; report that the result stopped at the cap and do not call it approved.

### Review result delivery

The reviewer ends its report with a machine-readable `<alphacode-review>` envelope; the assessment inside that envelope is the review's canonical verdict, and the markdown around it is analysis. If the task returns a review-delivery failure instead of a report, the envelope was missing, malformed, or written in an unsupported schema version: re-dispatch the review, and do not treat that failure as approval, as findings, or as a review with no findings.

### Required review prompt

Include all of the following in the task prompt:

- the request and acceptance checklist;
- the files and behavior changed;
- the unit boundary: base/head SHAs or `uncommitted working tree`;
- the full diff for this unit, without unrelated branch changes.

Ask the reviewer to end with one explicit assessment, for example:

```text
Assessment: Approved
```

or:

```text
Assessment: Needs fixes
```

A positive summary without that assessment is not approval. A review report is an instruction to act, not an acknowledgment: fix its Critical and Important findings in the same turn, re-review the resulting work, and correct the record if completion was already claimed. Minor findings can be addressed opportunistically unless the reviewer marks them as blocking.
