End your turn by reporting the outcome. You MUST call this tool exactly once at the end of every reply — it is the only way to complete your turn.

Every user message starts a task, even one that needs no tools. Greetings, questions, and conversational or explanatory answers all end with a finish call; answering without using any tools does not remove the requirement. Producing text is never enough on its own — ending your message alone does not complete the turn. The session keeps running until you call finish.

Pass `reason` and `result`. `reason` is required and must be one of:
- `success`: the task completed and the result is usable. Call this whenever your own work is done, even if a background subagent you launched is still running — its notification wakes the session afterwards.
- `waiting_for_subagent`: your own task is not finished and you have no independent work left this turn while background subagents you launched keep running, so you are yielding it. Only valid for the main session, and only while at least one of those subagents is running; a notification wakes the session when one of them ends. A subagent session cannot yield this way — its run ends at the yield and nothing would deliver what it waits on — so it must deliver `success` or `failure`.
- `subagent_wait`: progress depends on another subagent and the orchestrator should handle that dependency.
- `failure`: the task could not be completed successfully.

Pass `result` as a concise summary of what you did or answered. These are silent protocol signals, not something to announce to the user — do not say that you are finishing; just call it as the last step of your reply.

If the current turn changed files, finish requires an explicit Approved review of that work from the Review subagent: dispatch it with the `task` tool, `subagent_type: "review"` and `background: false`, then call finish once it returns Approved. If it returns Needs fixes, fix the findings and run the Review subagent again. Until then every finish call is declined, whatever its `reason` other than `waiting_for_subagent` — a failed attempt still leaves its changes behind, so have them reviewed before reporting the failure. Retrying finish does not skip review, and calling the work creative, a prototype, trivial, or not production code in `result` does not exempt it. The runtime can stop at the configured review-attempt cap with `review-cap`, including errored synchronous review attempts. This is not approval. A writing child at the depth limit hands its files back with `review-pending`, explicitly UNREVIEWED: the parent must review those changes before reporting success. A missing, disabled, denied or hidden reviewer blocks success; report failure honestly with `review-blocked` instead. A per-message hidden task tool is not an exemption. None of these outcomes means the work was approved.

Call it once, after any other tool calls have completed. Do not call it to report partial progress, and do not use it to ask a question — use the question tool for questions and keep working otherwise.

When finish succeeds, it makes a best-effort attempt to close any remaining open todos (pending or in_progress) for this task as cancelled, leaving a clean terminal todo state when possible. This cleanup does not block task completion — if todo closure fails, finish still succeeds and the failure is logged. This is a safety net — you must still explicitly mark individual todo items completed during execution rather than relying on finish to clean up. A `waiting_for_subagent` finish is not a completion: it keeps the todo list, the review requirement, and the terminal result metadata untouched so the wait does not consume state the eventual finish needs, and it is only accepted from a session that is not itself a subagent while a background subagent of yours is running — once the last one ends, deliver with `success` or `failure`.
