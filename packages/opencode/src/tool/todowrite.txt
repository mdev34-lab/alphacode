Create and maintain a structured task list for the current coding session. Tracks progress, organizes multi-step work, and surfaces status to the user. This is your primary execution-control mechanism, not just a checklist.

## When to use
Use proactively when:
- The task requires 3+ distinct steps or actions (not just 3 tool calls for a single conceptual step)
- The work is non-trivial and benefits from planning
- The user provides multiple tasks (numbered or comma-separated) or explicitly asks for a todo list
- New instructions arrive - capture them as todos
- You start a task - mark it `in_progress` (only one at a time) before working
- You finish a task - mark it `completed` and add any follow-ups discovered during the work

## When NOT to use
Skip when:
- The work is a single, straightforward task (or <3 trivial steps)
- The request is purely informational or conversational
- Tracking adds no organizational value

## States
- `pending` - not started
- `in_progress` - actively working (exactly ONE at a time)
- `completed` - finished successfully
- `cancelled` - no longer needed or abandoned at finish

## Granularity: one coherent unit per todo

One todo item must represent ONE coherent unit of work that you can execute and then mark complete. Do not bundle unrelated work.

Avoid broad phases:
- ❌ "Update model handling"
- ❌ "Update UI"
- ❌ "Add tests"
- ❌ "Create PR"

Prefer meaningful, verifiable units:
- ✅ "Trace current model-selection state flow"
- ✅ "Define next-turn configuration semantics"
- ✅ "Implement pending model state"
- ✅ "Apply configuration snapshot when creating the next turn"
- ✅ "Add model-switch test"
- ✅ "Run targeted tests"
- ✅ "Review final diff"

Rules:
- Complex tasks should naturally produce longer plans (10-16 items is normal for substantial work)
- Simple tasks should remain simple (2-4 items)
- Do NOT artificially inflate with trivial actions just to increase count
- Each item must be independently verifiable
- Break large work into smaller steps that can be completed and verified one at a time

## Execution discipline: one step at a time

This is the critical behavior. The normal loop MUST be:

1. Select next todo item
2. Work ONLY on that item
3. Verify that item is actually complete
4. Mark that item completed IMMEDIATELY after verification
5. Select next todo item

You MUST NOT:
- Create several todos then perform a large batch of unrelated work before marking anything complete
- Mark several independent items complete simultaneously unless they were genuinely completed as one indivisible operation
- Mark future work as completed because you expect it to succeed
- Mark work complete before verification (e.g., merely because code was written)
- Leave completed work in `in_progress`
- Use todo updates as retrospective bookkeeping after doing a large batch of work
- Have several unrelated items simultaneously in_progress (exactly ONE at a time)

Planning may be broad (you can inspect many files to understand). Execution must be narrow: one concrete todo as the current focus.

Example of correct execution:
- Todo "Trace how model configuration reaches the agent turn" is in_progress
- You may read multiple files and run searches to complete that investigation
- You do NOT simultaneously implement the feature, write tests, and create PR while that item remains active
- When tracing is done and verified, you mark it completed immediately, then move to next item

If you discover additional necessary work during execution:
- Update the plan rather than silently performing untracked work
- Add new todos for the discovered work
- If implementation diverges from original plan, revise the todo list so it continues to represent actual remaining work

## Completion and safety net

- Todo state is authoritative representation of progress; it must reflect reality at all times
- When an item is complete, mark it immediately — do not wait
- When blocked, keep it in_progress and add a follow-up todo describing the blocker
- The `finish` tool provides a final safety net: when it succeeds, any remaining open todos (pending or in_progress) will be automatically closed as cancelled, leaving a clean terminal state
- This safety net is NOT a replacement for disciplined updates — you must still explicitly mark individual items complete during execution

## Rules summary
- Update status in real time; don't batch completions
- Mark `completed` only after the required work is actually done, including any required verification. Never based on intent.
- Keep exactly one `in_progress` while work remains
- If blocked or partial, keep it `in_progress` and add a follow-up todo describing the blocker
- Preserve user-provided commands verbatim (flags, args, order)
- Items should be specific and actionable; break large work into smaller steps
- Never use the todo list as retrospective decoration
- Finish the todo state before ending the task, with `finish` providing a final safety net

## Examples

Use it:
- "Add a dark mode toggle and run the tests" -> multi-step feature + explicit verification
- "Rename getCwd -> getCurrentWorkingDirectory across the repo" -> grep reveals 15 occurrences in 8 files
- "Implement registration, catalog, cart, checkout" -> multiple complex features requiring granular breakdown

Skip it:
- "How do I print Hello World in Python?" -> informational
- "Add a comment to calculateTotal" -> single edit
- "Run npm install and tell me what happened" -> one command

When in doubt, use it.
