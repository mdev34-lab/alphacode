Delegate a bounded task to another agent and receive a machine-readable result.

Delegation is a first-class primitive, not a prompt: the child runs in an isolated session with its own agent, working directory, permission ruleset, and model. The child's full transcript stays in the child session (context firewall) — you only receive:

{ "status": "completed|error|timeout|cancelled", "summary": "...", "changedFiles": ["..."], "tests": [{"command": "...", "status": "passed|failed", "exitCode": 0}], "warnings": ["..."] }

Use delegation to cross the Work/Code boundary:
- From Work: delegate software-engineering tasks (code changes, debugging, refactors) to "code" inside a Git repository.
- From Code: delegate non-code work (document processing, general filesystem tasks) to "work".

Guidelines:
- Give the task a clear contract: goal, acceptance criteria, and constraints. The `constraints` fields (readOnly, allowCommit) become hard permission rules for the child, not requests.
- `readOnly: true` also hides the subagent tools (task/delegate) and MCP tools from the child, so it cannot hand its write access to another session.
- Commits are denied unless you set `allowCommit: true`. The rules cover the common `git commit` forms; if the repository HEAD still moves, the result carries a violation warning and you should treat it as unverified.
- `cwd` must stay inside the current workspace; the child operates there, and relative `changedFiles` are resolved against it.
- Delegation is synchronous: you get the result before continuing. Nested delegation is bounded by `subagent_depth`.
- Do not delegate to the agent you are, and do not use delegation to parallelize work that a single agent can do.
